# AGENTS.md

This file provides guidance to Code Agents (Codex, Cursor, etc.) when working with code in this repository.

## Development Commands

- `pnpm dev` - Start Next.js dev server
- `pnpm build` - Production build
- `pnpm test` - Run Vitest unit tests in `tests/unit/`
- `pnpm test:coverage` - Run unit tests with coverage thresholds
- `pnpm typecheck` - TypeScript type check (`tsc --noEmit`)
- `pnpm check` - Run `lint:check`, `typecheck`, `test`, and `build`
- `pnpm e2e` - Run Playwright E2E tests
- `pnpm e2e:production` - Run the production build smoke test
- `pnpm e2e:stripe` - Run the real Stripe sandbox E2E flow with Stripe CLI
- `pnpm e2e:creem` - Run the real Creem Test Mode E2E flow
- `pnpm e2e:waffo` - Run the real Waffo sandbox E2E flow
- `pnpm waffo:setup` - Register the Waffo webhook endpoint
- `pnpm e2e:ui` - Open Playwright UI runner
- `pnpm e2e:install` - Install Playwright browsers
- `pnpm lint` - Biome linter (auto-fixes with `--write`)
- `pnpm lint:check` - Biome check without writing changes
- `pnpm format` - Biome formatter
- `pnpm db:generate` - Generate Drizzle migration files from schema changes
- `pnpm db:migrate` - Apply pending migrations
- `pnpm db:push` - Push schema directly to DB (dev only)
- `pnpm db:studio` - Open Drizzle Studio GUI
- `pnpm email` - Email template preview server on port 3333
- `pnpm content` - Rebuild fumadocs MDX content collections
- `pnpm knip` - Find unused exports, dependencies, and files
- `pnpm auth:schema:generate` - Regenerate Better Auth schema to `src/db/auth.schema.ts`

Validate changes with `pnpm build`, `pnpm lint`, and targeted manual QA. Run
`pnpm typecheck` and `pnpm test` when changing typed logic, payment, checkout,
or URL handling. E2E
coverage exists for critical journeys and should be run locally when changing
auth, protected routes, public routing, profile settings, i18n routing, or shared
layout behavior.

## Architecture Overview

### Routing & i18n
- App Router with `[locale]` dynamic segment using `next-intl` (as-needed prefix strategy — default locale omitted from URL)
- Route groups inside `[locale]`: `(marketing)` for public pages, `(protected)` for authenticated pages, `auth` for login/signup, `docs` for documentation
- API routes at `src/app/api/` (outside locale segment)
- Translation files: `messages/en.json`, `messages/zh.json`
- i18n routing config: `src/i18n/routing.ts`
- Proxy (Next.js 16 replacement for middleware): `src/proxy.ts` — runs `next-intl` routing and cookie-based auth redirects; route constants and protected route lists live in `src/routes.ts`

### Authentication (Better Auth)
- Server config: `src/lib/auth.ts`; client: `src/lib/auth-client.ts`
- PostgreSQL adapter via Drizzle, session cached 1 hour, 7-day expiry, fresh age disabled
- Email/password login requires email verification; verification and password reset emails use the localized mail templates
- Plugins: admin, apiKey (`@better-auth/api-key`), emailHarmony (email normalization to block duplicate sign-ups)
- OAuth: GitHub + Google with account linking
- Auth hooks auto-subscribe new users to the newsletter when `newsletter.enable` and `newsletter.autoSubscribeAfterSignUp` are on (skipped in E2E mode)
- Auth tables in `src/db/auth.schema.ts` (generated by `pnpm auth:schema:generate`): `user`, `session`, `account`, `verification`, `apikey`

### Database (Drizzle ORM + PostgreSQL)
- Connection: `src/db/index.ts` using `postgres` driver (not `pg`), singleton pattern
- Schema: `src/db/schema.ts` re-exports `src/db/auth.schema.ts` (auth tables) and `src/db/app.schema.ts` (`payment`); migrations in `src/db/migrations/`
- Payment records track `type` (subscription/one-time), `scene` (lifetime/subscription), `status`; unique constraint on `invoiceId`
- Config: `drizzle.config.ts` reads `DATABASE_URL` from env

### Server Actions (next-safe-action)
- Three-tier action clients in `src/lib/safe-action.ts`:
  - `actionClient` — base, no auth required
  - `userActionClient` — requires authenticated session, ctx includes user/session
  - `adminActionClient` — requires admin role
- All actions use Zod schemas for input validation
- Actions organized by feature in `src/actions/`

### Payment System (Stripe, Creem, Waffo)
- Provider pattern in `src/payment/` with Stripe, Creem, and Waffo implementations
- Plans defined in `src/config/website.tsx`: Free, Pro ($9.90/mo or $99/yr), Lifetime ($199 one-time)
- Webhook handler validates signatures and synchronizes payment status and plan access
- Checkout flow: server action → provider checkout → hosted return → webhook updates the shared payment record
- Stripe and Waffo return through `/payment`, which polls the payment record before redirecting to Billing; Creem returns to Billing directly
- Webhook routes: `src/app/api/webhooks/{stripe,creem,waffo}/route.ts`, built with `src/payment/webhook-route.ts`; only the active provider's route accepts events
- Plan and price validation: `src/lib/price-plan.ts`; provider setup: `docs/modules/PAYMENT.md`.

### Provider Pattern (used throughout)
All external integrations follow a pluggable provider pattern with factory functions:
- Payment: `src/payment/` (Stripe, Creem, Waffo)
- Mail: `src/mail/` (Resend, React Email templates — all localized); see `docs/modules/EMAIL.md`
- Newsletter: `src/newsletter/` (Resend, Beehiiv, MailCheap); see `docs/modules/NEWSLETTER.md`
- Notifications: `src/notification/` (Discord, Feishu)
- Storage: `src/storage/` (S3 via `s3mini`); see `docs/modules/STORAGE.md`
- AI: `src/lib/ai/gateway-demo.ts` and `/api/ai/demo` (six Vercel AI Gateway examples); models in `src/lib/ai/ai-models.ts`, schemas in `src/lib/ai/demo-schema.ts`, setup in `docs/modules/AI.md`. Independent cards in `src/components/ai/` own each demo's parameters and result rendering; the page explicitly composes them. `use-ai-demo.ts` shares request state. Speech uses the Gateway REST API with AI SDK 6.

### State & Data Flow
- Server components fetch data directly; mutations via server actions
- AI demo forms submit to `/api/ai/demo` through the shared `use-ai-demo` hook
- Zustand stores in `src/stores/` for client-side state
- React Query for async data on client
- Forms use React Hook Form + Zod validation

### Content
- Fumadocs for documentation (`content/docs/`), MDX blog (`content/blog/`)
- Source config: `source.config.ts`; rebuild with `pnpm content`

### Configuration
- Centralized app config with feature flags: `src/config/website.tsx`
- Demo mode: `NEXT_PUBLIC_DEMO_WEBSITE` env var (enables Crisp chat, Turnstile captcha, and API key management)
- Environment template: `env.example`

## Code Style

- Biome enforces: 2-space indentation, 80-char line width, single quotes, ES5 trailing commas, semicolons required
- Filenames: kebab-case (`dashboard-sidebar.tsx`); hooks prefixed `use-` (`use-session.ts`)
- Named exports preferred; default exports only for pages/layouts and React Email templates/components in `src/mail/`
- Server-only code marked with `"use server"` directive
- Tailwind CSS v4 with tokens in `src/styles/`
- UI primitives from Radix UI; icons from `lucide-react`
- Keep reusable docs, test fixtures, comments, logs, and error messages
  product-neutral. Mention this repository or a sibling product only when its
  identity is part of the documented behavior or configuration.

## E2E Testing

- Config: `playwright.config.ts`; specs: `tests/e2e/specs/`; catalog: `tests/e2e/TEST-CATALOG.md`
- E2E runs against a dedicated local Next.js server on port `3100` using `.next-e2e`, so it can run while normal `pnpm dev` is using port `3000`.
- E2E mode sets `NEXT_PUBLIC_DEMO_WEBSITE=true`, disables Turnstile with `NEXT_PUBLIC_E2E_TEST_MODE=true`, and sets `E2E_TEST_SECRET`. In development with that secret (`src/lib/e2e.ts`), the app skips mail sending, sign-up newsletter auto-subscribe, and payment notifications and enables `/api/e2e/users` to clean/verify `e2e-*@example.test` accounts.
- `pnpm e2e:production` builds and serves the app with `next start` and runs `tests/e2e/production/`.
- Keep E2E local-first. CI should prefer fast `pnpm lint` and `pnpm build` unless a dedicated E2E environment is explicitly configured.
- Stripe sandbox testing accepts `STRIPE_ENV_FILE=/path/to/project/.env pnpm e2e:stripe`; it requires an `sk_test_` key, matching Price IDs, and the Stripe CLI.
- Provider sandbox suites use their own ports and dist dirs: Stripe `3119`, Creem `3120`, Waffo `3118` (override with `STRIPE_E2E_PORT`, `CREEM_E2E_PORT`, `WAFFO_E2E_PORT`). Creem and Waffo need a manual HTTPS tunnel and webhook registration; see `tests/e2e/{stripe,creem,waffo}/README.md`.

### E2E Workflow

Use `Spec -> Code -> Verify -> Test -> Green` proportionally when a user flow,
route, interaction, or behavioral contract changes:

1. **Spec**: update `tests/e2e/TEST-CATALOG.md` with the acceptance journey.
2. **Code**: implement the feature.
3. **Verify**: run the app and walk the real UI in a browser.
4. **Test**: add or update the relevant Playwright spec.
5. **Green**: run the related spec locally; run full `pnpm e2e` before releases
   or broad refactors.

Do not automatically update the catalog or Playwright specs for a small UI,
styling, copy, icon, or link change. Prefer focused static checks and, where
useful, targeted browser verification without editing test files. Add or change
E2E coverage only when the user explicitly asks for tests, an existing test
needs repair, or a change materially alters a critical user journey or behavior
contract.

### E2E Test Intent And Maintenance

E2E tests protect functional journeys and outcomes, not presentation contracts.
Validate navigation and redirects, form submission, request results,
permissions, persisted data, and the availability of controls required to
complete a journey. Prefer API or database-backed state when it establishes the
result more directly than rendered UI.

- Presentation-only changes must not require E2E catalog or spec changes.
  Functional E2E tests do **not** assert exact wording, translations, headings,
  toast copy, element placement or order, spacing, dimensions, colors,
  typography, icons, images, CSS classes, or other visual styling.
- For product-owned controls that a journey must operate, add an unlocalized
  `data-testid` named for the behavior, then use that selector in the spec. Keep
  these IDs independent of visible copy. Use form field names, URLs, and
  response or data assertions where they are already stable. Do not add IDs
  solely for static content checks.
- Locators identify controls; they are not assertions about how those controls
  are presented. Text assertions remain appropriate only when text itself is
  the product contract, such as generated content, an email payload, or a legal
  notice. Third-party hosted-payment field labels belong to their
  sandbox-provider compatibility tests, not to product-copy checks.
- Handle accessibility requirements in dedicated tests when explicitly in
  scope. Add visual-regression tests only when the user explicitly requests
  them; do not mix either concern into functional E2E flows.

## Commit Messages

Use `type(scope): summary`. The scope is required and should identify the
affected module or concern. Do not use bracketed prefixes such as `[fix]`,
`[feat]`, or `[chore]`.

Allowed types include:

- `fix(scope): summary`
- `feat(scope): summary`
- `chore(scope): summary`

Examples:

- `fix(payment): handle duplicate webhooks`
- `chore(ui): update component tooling`
- `feat(email): add delivery status tracking`
